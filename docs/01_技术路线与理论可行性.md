# 技术路线与理论可行性

> 状态：FROZEN
> 适用版本：V1.5-R / V1.5-T
> 最后更新：2026-09-22
> Owner：Ship-Unloader Engineering

## 1. 问题定义

卸船机顶部双 LiDAR 面向散货船，核心任务不是“找一个矩形”，而是：

1. 在目标船内区分 1 / 2 / 3 个真实 Hatch；
2. 避免把 Cargo、码头、围板外侧、坡脚识别成舱口；
3. 对每个 Hatch 找到真实 opening-side 结构边；
4. 遮挡时保留不确定性，而不是幻觉；
5. 船漂移时全部 Hatch 作为同一刚体随船运动。

因此任务本质为：

> **高召回结构 Proposal + 局部 3D 几何验证 + 多 Hatch 联合假设 + 证据化边界 + 单一刚体坐标系。**

## 2. 为什么不能继续依赖 Global Deck

真实场景存在：

- Cargo 高于 Deck；
- 多船并排；
- 码头与船甲板高度接近；
- 舱底 / Cargo / Deck 多层混合；
- 点云视角导致结构面缺失；
- 船体姿态变化。

因此全局单一 Deck winner 容易把：

```text
Cargo top
反向舱底
码头
其它船
```

错误解释为目标船甲板。

结论：

> **Global Deck 可以做研究诊断，但不能成为 V1.5-R Production 的必要前置。**

## 3. Proposal 层

### 3.1 Geometry Proposal

目标：

> 宁可多给候选，也不能漏掉真实 Hatch。

使用：

- 多层高度结构；
- 局部边缘；
- 开口/腔体趋势；
- 局部 Deck 邻域；
- 连贯结构支持；
- 负结构冲突。

Geometry Proposal 输出粗区域，不直接输出最终钢边。

### 3.2 Legacy CNN Proposal

旧 `hold_detector` 可蒸馏：

- Heightmap；
- 滑窗；
- CNN score；
- NMS；
- hard negative 思路。

不得继承：

- 单舱最终选择；
- Y-min 真值；
- 旧固定搜索范围真值；
- 旧 Top-5 即完整召回；
- CNN rectangle 即 Hatch boundary。

只有当 CNN 对 Geometry Proposal 有**独立召回增益**时才保留为可插拔 provider。

## 4. 1 / 2 / 3 Hatch 联合求解

不能逐框贪心，因为：

- 一个大框可能跨两个 Hatch；
- Top-K 可能全是同一 Hatch 的重复；
- 隔板弱时 H=1/H=2 都可能成立；
- Cargo 会产生高分伪候选。

因此必须显式比较：

```text
H=1
H=2
H=3
```

评分应由多个证据组成：

```text
proposal_support
local_deck_support
opening_side_support
partition_support
negative_conflict
unexplained_observation
duplicate_penalty
cross_vessel_penalty
```

复杂度先验只能用于证据近似相同时破平局。

## 5. Local Deck

Local Deck 只使用 Hatch 候选外围、与目标船结构连续的实测点。

必须排除：

- Cargo interior；
- Wharf；
- UNKNOWN 空白；
- 错误 global winner。

建议使用：

- robust plane fitting；
- 多方位 ring support；
- residual distribution；
- normal consistency；
- competing plane rejection。

失败：

```text
LOCAL_DECK_UNRESOLVED
```

禁止回退 Global Deck。

## 6. Opening-side Boundary

物理定义：

> **Deck datum 上面向舱口开口内侧的真实结构转折。**

主要路径：

### 6.1 OBSERVED_PROFILE_BREAK

从原始 3D 点云沿候选边方向采样多条横断面：

```text
Deck ──────┐
           │
           └─ opening / interior
```

每条 profile 独立检测 Deck → opening/interior 的结构变化，再对多个 break position 鲁棒拟合最终边。

### 6.2 OBSERVED_3D_FACE

如果雷达实际采到连续竖直结构面：

- 提取面支持；
- 与 Profile Break 并行验证；
- 不要求所有场景必须存在。

### 6.3 Boundary Fusion

输入：

```text
Profile Break
3D Face
BEV contour (auxiliary only)
candidate geometry
```

输出：

```text
line / segment
support count
residual
visibility
uncertainty
evidence_type
```

## 7. 为什么 Cargo 轮廓不能当钢边

Cargo 会随作业持续变化，而且可能：

- 高于围板；
- 与开口边接触；
- 覆盖隔板；
- 形成规则直线；
- 形成坡脚。

因此：

```text
Cargo outer contour
Cargo toe
Cargo top edge
```

只能作为冲突/遮挡证据，不得升级成 `OBSERVED_*` 钢结构边。

## 8. 遮挡理论边界

### 部分遮挡

若仍存在部分钢边或可靠历史：

```text
PARTIAL
HISTORICAL_MODEL
HATCH_COUNT_AMBIGUOUS
```

均是合法输出。

### 首次完全覆盖 + 无历史

此时隐藏边没有充分观测。

允许：

```text
PRIOR_ONLY
OPERATOR_CONFIRM_REQUIRED
INSUFFICIENT_OBSERVATION
```

不允许：

```text
OBSERVED hidden boundary
厘米级隐藏边精度声明
```

这是物理可观测性限制，不是算法优化问题。

## 9. 理论可行性分级

### 已有工程基础，可实现

- 严格 PCD/PLY XYZ 解码；
- BEV / heightmap；
- Geometry proposal；
- 旧 CNN proposal；
- 局部平面拟合；
- 3D profile；
- robust line fitting；
- 固定 Ship Frame；
- V1.4 SE(3) 跟踪接口。

### 当前合理但必须实测证明

- 9 个 Development Hatch 全召回；
- 双舱/三舱不合并；
- Local Deck 排斥 Cargo/Wharf；
- opening-side 实测精度；
- 部分遮挡下结构不被 Cargo 改写；
- 真实船漂移下统一刚体跟随。

### 物理上不能无条件保证

- 首次全遮挡无历史时精确恢复隐藏钢边；
- 无有效船体位姿时输出当前世界精准 Hatch；
- 没有独立 Golden GT 时声明厘米级真实精度。

## 10. 最短研发决策树

```text
Proposal Baseline
        │
        ├─ 9 Hatch 未召回
        │      → 修 Proposal / NMS / Hypothesis
        │
        ▼
Oracle Local Geometry
        │
        ├─ Oracle 失败
        │      → 先修 Local Geometry
        │
        └─ Oracle 成功
               → 接 Product Proposal
```

这个顺序用于保证每个失败都能归因。
