## 前提

使用本分支代码、Python 3.8、NumPy、SciPy 与仓库现有的 `jsonschema` 工具依赖。PCD 保留在 `Ship-Unloader-Data/legacy/hold_detector/`；所有运行输出保留在忽略的 `Ship-Unloader-Work/`。不读取 `map.zip` 派生 PLY、clean/aligned/cut PLY、sealed holdout 或 Hatch GT ROI。

从仓库根执行：

```bash
python -m ship_perception.r1_static.batch \
  --dataset-manifest ship_perception/datasets/v15_dataset_manifest.json \
  --data-root Ship-Unloader-Data/legacy/hold_detector \
  --scene-set normal6 \
  --output-root Ship-Unloader-Work/r1_static \
  --run-id baseline_001
```

批处理固定选择 08-01、08-08、4-16、6-8、7-16、8-22 六个 Development ID，但 PCD 路径和预期 SHA256 均从 manifest 读取。ID 只用于输入选择与目录命名，不进入几何评分。

## 检查顺序

1. 查看 `baseline_001/batch_summary.json`，区分 `RESOLVED`、`NO_CONFIRMED_HATCH`、`HATCH_HYPOTHESIS_AMBIGUOUS` 和 `RUNTIME_ERROR`。检查每场景 `result.json` 的 `input_sha256`、`point_count`、`config_hash` 与 `coordinate_frame`。
2. 在 CloudCompare 打开 `scene_debug.ply`；再对照 `proposal_debug.ply`、`local_deck_debug.ply`、`boundary_debug.ply`。以灰色 Raw 点云判断是否真有 opening-side 钢结构支撑，不依据粗轮廓或黄中心判断边界正确。
3. 对照 `profile_debug.json` 查看每条边的有效横断面、Deck 与 lower-return 数量、break 位置和失败原因。单侧甲板或竞争平面应保持失败。
4. 填写 `baseline_001/人工复核.csv`：逐场景记录舱数、位置、漏检/误检、合并/拆分和可观察边的大致偏差。此表为人工反馈，不是商业 Golden。
5. 第二轮必须用新的 `run_id` 和 override 文件；使用 `python -m ship_perception.r1_static.compare baseline_001 <new_run_id>` 查看中文对比 CSV。首轮结果禁止覆盖，也不按已知舱数在同一提交中调参。

当前 Windows 首轮结果应与 Ubuntu 独立运行结果并列保存，尤其检查解码 SHA、点数和 bbox 是否相同。Ubuntu 差异需附命令、环境、软件 SHA、配置 SHA、stdout/stderr 和 artifact 路径，不能直接改判门禁。

## 门禁与边界

执行 R1 合成单测、R0 measurement 单测、`git diff --check` 与 V1.4 frozen verifier。真实 Development 场景的未解析结果原样归档。正式 R1 acceptance 仍要求六场景舱数全正确、9/9 实例召回和独立 opening-side 物理边检查；本手工复核不替代该门禁。

R1-S0 不生成 Ship Frame，也不接动态跟随。若要将 Python 结果并入冻结的 C++ Production 链，先进行 Architecture Review，明确 target-vessel seed、Ship Frame 与 Evidence 契约。
