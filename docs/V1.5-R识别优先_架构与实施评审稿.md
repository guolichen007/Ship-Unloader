# V1.5-R 识别优先：1～3 舱结构识别与整船刚体跟随

> 状态：基于当前仓库、九份 Development 原始 XYZ 可视核对及 V1.5 P0-3 Shadow 失败证据形成的**架构与实施评审稿**。它确定开发顺序、数据/算法/验收边界；不宣称真实舱数、真实边界厘米精度或现场跟踪已验证。当前产品代码不因本文改变。

## 1. 唯一当前目标

对**当前作业目标船**，识别视野内可见的 1～3 个敞口舱口，逐边保存观测、推断与未知证据；船运动时整组舱口共享一个船体位姿。先完成可见舱口 R1，再处理局部遮挡 R2；完全遮挡 R3 与现场刚体跟随 T1 必须有各自数据和门禁。暂停控制、PLC、Cargo Map、新大型语义网络、Web 和新滤波器。

真实产品允许 `NO_CONFIRMED_HATCH`、`HATCH_COUNT_AMBIGUOUS`、`TARGET_VESSEL_UNRESOLVED`、`LOCAL_DECK_UNRESOLVED`、`POSE_INVALID`。业务通常 1～2 舱、允许 3 舱，是弱先验，不是把不存在的证据变成观测。若有 4+ 舱或非适用船型，报告 `OUT_OF_SCOPE`，不强并为 3 舱。

## 2. 当前仓库给出的硬事实

1. `hold_detector/` 只读。其推理在 0.5 m 高度图上枚举绝对 Y 起点 1.5～7.5 m、长 25～105 m 的窗，NMS 只留 Top-5，最终选择一个靠码头的目标。**去掉最终 Y 最小选择并不自动得到多舱召回**：搜索范围、门控、框长和 NMS 都可能漏掉单独舱口。
2. 旧 13/13 检出及约 0.76 弱矩形 IoU 是历史**单目标、训练样本相关**基线。旧训练脚本遍历 `detect/pcd` 全部标注，评估只取每文件第一份标注；现成权重不能证明四份封存集的独立泛化。更关键的是，旧负样本生成只避开当前 partial 标注框，扫描内未标的另一个舱可能被错误采成负例；不能直接沿用这个训练流程做多舱。
3. 13 个独立 XYZ 扫描、12 个有标扫描、23 份逻辑 partial annotation、11 份额外重复/近重复标注的事实保持。每个旧标注只覆盖一个舱口；整船舱数、逐边可见性和目标船归属没有现成 GT。
4. 九份 Development 的可视图表明：`final_map_8_22_cut` 未标但有三个分隔明显的低表面候选，尚不能仅凭俯视图认定为三个舱；`final_map_5_29_2d_005` 与 `final_map_7_2_005` 有并列的多个长条船形区域。后者是否多船/背景需人工核定，**一张 PCD 的长条区域数不能直接当作一条船的舱数**。
5. 当前 V1.5 产品的真实 Development Frame/Deck 联合仅 6/9，非歧义弱标关联 0/8；合成开发子集通过不等于真实完成。P0-3 Shadow 显示上层 Deck 候选能生成，但缺少可统一排除反向舱底、Cargo 的物理方位/归属判据。因此全局 Deck 不再阻塞新生产识别链。
6. V1.4 有整船 SE(3) 跟踪基础接口及无效帧/地图修订保护；真实船移动、满载遮挡、同步和动态点下的现场精度仍待验证。V1.4 累积云含动态返回，不能直接称为静态语义地图。

## 3. 三份契约

### 3.1 Dataset Contract

首先确定**目标船**，再标舱口。开发期只看九份 Development；四份 sealed weak holdout 不用于调参与架构定阈。目标船粗 ROI 的来源可以是作业计划/泊位区域或操作员正常输入，必须在运行时可获得、可追溯；评分时的人工舱口框不得伪装成此输入。若现场不能提供这种粗目标指示，则“从全场景自动选作业船”是 R1 前置 P0，须单独做目标船归属门禁，不能偷偷用最小 Y 代替。若一帧含多个可能船体又无可信目标指示，输出目标归属不明。

每份扫描记录：`target_vessel_roi` 及来源、`fov_coverage`、`visible_in_fov_hatch_count`、`whole_vessel_hatch_count`（可为 UNKNOWN）、每舱粗 polygon、逐边实测跨度和观测状态、可见隔板端点、争议说明、标注者与复核者。**视野内舱数与整船总舱数不能共用一个字段**。多份弱框及数字别名按物理扫描分组，不增加舱数。

R0 的人工框只支持舱数、实例召回、误合并/重复和粗 IoU；逐边 15～20 cm 必须等有物理开口内缘定义、充分点云与双人复核的 Golden 边界标注。13 个静态 XYZ 不是 13 条独立船，也不是移动/渐进揭示时间序列。现成 CNN 训练过程已接触全部旧标注；若要保留封存集的比较价值，必须至少在九份 Development 上重训权重，最终泛化仍须新采、未见过的船和时序。

### 3.2 Algorithm Contract

生产输入 `Raw XYZ + target_vessel_seed/可信作业范围 + 可用传感器标定与姿态`。候选链为：严格解码 → 目标船粗范围 → **几何 proposal 与经验证可增益的 CNN proposal 并集** → 1/2/3 舱及误合并竞争假设 → 每个假设局部 Deck/3D 证据 → 一对一 Hatch 组装。现有 CNN 以 PCL 点云、自定义权重文件和固定尺寸高度图运行，适合作为 R0 候选召回基线，不直接复制为 Geometry Core 依赖。只有 Development-only 重训/审计后，证明它对几何提案有独立召回增益，才把其不依赖 PCL 的推理适配器接入产品。旧模型的绝对 Y、长度、NMS 和单舱最终选择均不保留为物理规则。

几何 proposal 先从目标范围内的**实测多层表面**寻找连贯的 Deck 邻域与相邻下降/腔体、局部边缘支持和闭合趋势；允许顶部 Cargo 使开口内部高于 Deck，此时改由可见 opening-side 结构环和跨帧已确认结构提供候选，不把“低洼”设为必要条件。粗尺度只以高召回提供宽松区域，候选经过局部原始 XYZ 验证才成为边。背景连通、码头平面、高吊臂和货堆线状物都作为竞争/否决证据。若全遮挡且无历史，proposal 可以为空并输出证据不足。

局部 Deck 只从候选外围**实际测得、与目标船连贯相接**的结构点稳健拟合；Cargo 内部、码头和空白未知单元不算甲板支持。至少检查多个方位的支持、残差、法向与相互竞争平面。默认环带宽度是待验证配置，不把 4 m 当物理真理。无足够证据时停止局部精化；禁止回退到错误 global Deck。

Hatch Boundary 的物理定义仍为 **Deck datum 上面向开口内侧的结构转折**。当前顶视点云常缺连续竖直立面，所以多条原始 3D 横断面的 Deck—下降过渡及舱内支持是主要实测路径；可见竖直面是并行路径，不能设成必需。0.5 m 网格、BEV 轮廓和 CNN 矩形只作候选/交叉验证。转折不唯一时输出区间与 `PARTIAL`，不以货堆外缘、坡脚、外侧围板或固定高度等值线冒充内边。

每条边保留 evidence、visibility、实际支持区间、端点是否受约束与可空 uncertainty。`OBSERVED` 必须有实测支持；`INFERRED`、`HISTORICAL` 和 `UNKNOWN` 不得转换成虚假的 observed。静态 XYZ 无射线时，缺点默认 UNKNOWN；只有可靠传感器视线或跨时序观测才可断言当前被遮挡。联合假设求解保留 H=1/2/3 的竞争分数和差距；无法分辨隔板时为 `HATCH_COUNT_AMBIGUOUS`。

候选假设的比较对象是**同一目标船、同一可见范围**里的 1、2、3 个 opening，而不是全图低洼连通域数。每个假设记录提案来源、Deck 支撑、opening-side 转折支撑、端点/隔板证据、与 Cargo/Wharf 的冲突和未解释的观测；先施加物理必要条件，再比较归一化分数。低复杂度先验只能打破证据接近时的平局，不能把“两舱隔板被料盖住”硬压成一舱。跨帧关联时，已确证边可带来源与年龄保留为 `HISTORICAL`，新观测只更新它确实约束到的边；冲突需隔离并触发复核，不直接把 Cargo 外形写成历史钢边。

每舱局部坐标 `F_i` 仅用于拟合，最终所有舱口统一转换到**同一个固定 Ship Frame B**。离线 R1 可使用明确来源的 provisional B，记录艏艉 180° 歧义；V1.4 集成使用其固定 B，不重新旋转整个船体。最终 `candidate_id` 不是物理舱号。`P_hatch^W(t)=T_W_B(t)P_hatch^B`；不得为每个舱估独立漂移。

运行时分开**识别节拍**与**跟随节拍**：R1 在初次积累到足够结构观测或证据变化时计算/复核 1～3 舱模型；T1 每个有效跟踪帧只用同一个 `T_W_B(t)` 更新世界位置。重识别结果进入 shadow candidate，与固定 B 的历史结构逐边核对后才晋升，不能因一帧料堆变化立即改写钢边。当前 pose 失效时，模型可留在 B 供恢复后重用，但当前世界输出无效；不得继续外推成“实时精准跟随”。这复用 V1.4 的有效帧与 revision 防污染思路，不新增 EKF 或控制接口。

### 3.3 Acceptance Contract

R0 先分开量化三个瓶颈：`PROPOSAL_RECALL_PRE/POST_NMS`、`ORACLE_LOCAL_GEOMETRY`（评分通道给真 ROI）和 `PRODUCT_LOCAL_GEOMETRY`（真实 proposal）。Oracle 的真 ROI 绝不进入产品输入。如果 oracle 已失败先修局部几何；oracle 成立而 product 失败再修 proposal/假设求解。

R1 只针对已核定目标船且覆盖明确的扫描判定：视野内舱数、逐舱召回、跨舱误合并、局部重复、Wharf/Cargo 假舱、逐边 observed/inferred 状态、粗 IoU。未核定整船完整覆盖的扫描不能计入“整船舱数正确”；无法确认的例子显式留在分母与未决列表，不能静默删除。九份 Development 是调试集；四份原封存集仅一次性诊断，最终商业泛化需要独立新船数据。弱框不承担 15/20 cm 精度门。

R2 分别验证单边被料覆盖、隔板被料覆盖和高于围板的料堆。检查隐藏钢边不被货物轮廓替代、双舱不因隔板暂时不可见而被错误合并、无历史时只报告竞争假设。合成遮挡主要验证**不造假**；真实满载准确性仍需现场数据。

R3 历史模型只保存几何。若当前 `T_W_B` 无效、超时或失去结构支撑，世界舱口位置也无效；不能用历史 geometry 掩盖 pose 丢失。首次全覆盖且无历史时，只能提供 `PRIOR_ONLY` 与需人工确认状态，不能宣称隐藏边精度。

T1 采同一船有时间戳、传感器姿态、卸料前后和位姿参考的序列；验证整船平移、升沉、纵倾、横摇、偏航及货物变化时 1～3 舱相对几何刚性、世界位姿误差和失败状态。只在有效帧更新世界位姿；动态货物不能进入可确认结构的跟踪目标。现有 V1.4 合成成绩不能替代这一门。

### 3.4 遮挡与跟随的运行状态

| 场景 | 可采纳证据 | 允许输出 | 禁止输出 |
|---|---|---|---|
| 开口内缘和局部 Deck 可见 | 多横断面夹定的转折、实测边/角 | `OBSERVED` 边和已确认舱候选 | 以 0.5 m 栅格边直接宣称厘米精度 |
| 沙土遮住一条或多条边 | 其余可见钢边、可靠历史、独立隔板证据 | `PARTIAL`，历史边另标来源、年龄、当前可见性 | 将料堆轮廓升级为当前观测钢边 |
| 两舱间隔板被料盖住 | 两个各自开口的外侧证据；先前已确认的分舱历史 | 1/2 舱竞争假设，证据不足时 `HATCH_COUNT_AMBIGUOUS` | 把两个舱无证据合并，或靠“常见两舱”凭空分裂 |
| 首次全遮挡、无历史 | 作业先验最多提供粗位置 | `PRIOR_ONLY`、需人工确认、不能用于精确边界 | 声称识别了隐藏开口和隔板 |
| 船随水漂移且位姿有效 | 同一船体的稳定结构与传感器时序 | 固定 B 内舱几何，经 `T_W_B(t)` 整体变换 | 每舱各估一个独立漂移 |
| 当前船体位姿无效 | 上次有效估计仅供预测 | 世界边界 `POSE_INVALID`，冻结结构更新 | 用历史舱几何伪装当前世界位置有效 |

静态 XYZ 没有传感器射线或时间关联时，点缺失只能记 `UNKNOWN`。`OCCLUDED` 需要当前射线/遮挡几何，`HISTORICAL` 需要先前确证并带有效位姿链；这些状态不能互换。

## 4. 最短且可归因的实施顺序

1. **R0-A 数据补全**：九份 Development 的目标船/视野/视野内舱数/粗区域由两名审阅者独立确认；`final_map_8_22_cut` 的三个开口状区域和多条并列船形场景先核查。重复标注只作分歧证据。四份封存数据由独立人员持有，不给算法开发者看评分结果。
2. **R0-B 旧版候选基线**：先把现成权重作为有泄漏风险的历史诊断，记录 NMS 前、NMS 后的 Top-K；同时输出几何候选。若 R0-A 标注足以训练新模型，只用 Development 且对**所有已确认可见舱**建正例，未知/未标区域不得作负例，再测每舱召回与几何分支的互补增益。禁止 Y 最小最终选择，审计旧 y/长宽先验是否造成漏检。保留旧只读目录，新代码在 `ship_perception/`。
3. **R0-C Oracle Local Geometry**：给真实粗 ROI 的隔离诊断通道，测局部 Deck、opening-side profile 与可见面、Polygon/Partial；对每个失败分 `LOCAL_DECK / BOUNDARY / TOPOLOGY / INSUFFICIENT_OBSERVATION`。此时不把 GT ROI 暴露给 runtime。
4. **R1 Product**：接候选并集和 1～3 舱联合求解，输出统一 B 中的候选与逐边证据；固定配置、做真实 Development 和负例回归。只修观察到的失败层。
5. **R2 → T1 → R3**：R2 建立不造假遮挡能力；R1 成立后可接 V1.4 做 T1 时序验证。R3 的“历史保持”以 T1 当前位姿有效为前提，不能先宣称全覆盖仍可准确跟随。

R0 完成后才决定 R1 的首个代码改动是 candidate 召回还是 local geometry。这个决策不改变以上生产输入、单一 Ship Frame、逐边证据与 fail-closed 架构。

## 5. 标注与验收的可执行冻结点

R0 标注先看**无旧弱框的盲审图和原始 3D**，两名审阅者分别保存独立文件及 SHA-256；互不看对方结论。随后才对照旧弱框，第三步裁定目标船、视野范围、可见舱数、粗 polygon 和逐边证据。裁定记录两份独立文件摘要与争议理由。草稿 schema 和验证器见 `ship_perception/datasets/v15r_visible_hatch_manifest.schema.json`、`ship_perception/tools/validate_v15r_visible_hatch_manifest.py`；当前九份草稿的 `scoring_ready_scan_count=0`，不能作为 GT。若粗 ROI 来自人工**评分标注**，只准在 Oracle 诊断使用；产品要有独立的、运行时确实可得到的目标船 seed。

R1 的放行先要求每个可计数实例的来源链、全部扫描的明确结果/失败状态、零伪造 observed 边及零把负控制确认为完整舱；实例召回、误合并、局部重复和边误差逐例报告。Development 用来定位失败，不宣称泛化；真实边的厘米精度只由新建 Golden 且双人复核的物理开口内缘承担。R2、T1 分开验收，不能用 R1 静态数据抵扣。正式阈值要在独立标签和时间序列齐备后冻结，不能用当前未核定舱数拍出一个漂亮的通过率。

最小合成矩阵固定为：一、二、三舱；单个长舱与相邻双舱的竞争；斜边和非矩形；只有局部视野；Deck—斜坡—舱内过渡但无竖直面点；外侧围板、码头、起重机、货堆负例；仅一边被料覆盖；双舱隔板被料覆盖；首次全遮挡；船体 6DoF 运动叠加动态料堆。逐例检查实例一对一、额外完整舱为零、观测/历史/未知标签、边误差和当前位姿有效性。合成结构真值仅在评分通道，不能进入 proposal、局部 Deck 或跟踪。

真实 Golden 与 T1 采集必须补齐：目标船作业身份/粗范围的正常运行时来源；同一船在空舱、半载、料高过围板时的多时刻原始双雷达扫描；每点时间、两雷达外参、吊机 `T_W_C(t)`；独立测得的钢结构 opening-side 边/隔板与船体世界位姿参考；FOV 和可见性裁定。采集前先约定目标船与实际舱数，不把旧 weak 框升格为独立 GT。没有这些记录时，只能完成静态 Development 诊断，不能宣称满载遮挡下识别准确或随水漂移的现场精度。

## 6. 理论与可行性结论

- **可实现的已知基础**：严格 XYZ 解码、BEV/旧 CNN 候选、高度环带、现有 3D profile/边界类型、V1.4 SE(3) 接口均已在仓库；Proposal 与局部精化作为任务分解合理。
- **尚未证明的工程能力**：在九份真实 Development 上无 GT 泄漏地确定目标船、多舱 Top-K 召回、Local Deck 对 Cargo/Wharf 的排斥、真实 opening-side 精度，以及有货/漂移时的位姿保持。它们需要上述独立门禁，不能从现有 129/129 合成开发子集推出。
- **物理不可保证项**：首次全覆盖、无历史且无可见钢结构时，隐藏舱边和隔板没有充分观测，不能保证厘米级恢复；结构与船体定位证据均失去时，历史模型也不能保证当前世界位置。

本阶段的成功不是一个漂亮平均 IoU，而是：**在目标船归属明确的前提下，看到的每个舱都被分别识别；看不清的边保持不确定；已确认的 1～3 个舱作为一个刚体模型，在有效船体位姿下整体移动。**
