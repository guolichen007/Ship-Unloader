## 已证实的旧问题与本轮改变

旧 `proposal_debug.ply` 用 Proposal AABB 的整根 Z 柱染紫，6-8 与 8-22 分别误染 695865/701989 和 892434/1027532 个原始点。旧 `local_deck_debug.ply` 用包围盒、平面残差重新猜绿色支持点；6-8 p001 算法接受 1744 点而绿色只有约 228 点。旧假设求解器还把被选中的 PARTIAL 当成 `RESOLVED` 和一舱确认。

现在紫色原始点严格由 `SeedComponent` 网格单元映射，绿色严格使用算法接受的 raw ID。Proposal 包围盒单独画线；旧全局 `estimate_local_deck` 仍输出诊断和所有候选平面的点级归属，但不控制 OpeningSeed 的生成。结果 schema 升至 `ship_perception.v15r.static_result.2`，明确 selected、partial、unresolved、complete 与 confirmed；只有 `COMPLETE_OBSERVED` 增加 confirmed。

主链为 `Proposal → fine OpeningSeed（coarse 仅作支持）→ 外部 flood fill 所得外轮廓 → PerimeterSegment → 每段外侧支持带及独立甲板平面 → 每边 Profile Break/3D Face → observed-only 边界`。轮廓内部孔洞不产生外环；段的甲板候选要求重力相容、宽度、沿边覆盖和跨度，多个独立合格平面只标记该段 `SEGMENT_DECK_AMBIGUOUS`。每条边复用已有 Profile/3D Face 物理阈值，不补未观测边、不强制矩形。FOV 外部连通区域使扫描边界种子为 `PARTIAL_FOV`，不允许它变为 COMPLETE。

- **Gate A 通过：** 六场景逐点解析二进制 PLY，`proposal_debug.ply` 紫色 raw ID 与所有真实 seed cell 对应的 ID 完全相同；`local_deck_debug.ply` 绿色 raw ID 与所有已接受 segment support ID 并集完全相同。六类约定 PLY 均存在；每段 `.npz` 保留 strip、全部候选和选中 raw ID，候选 PLY 便于查验。
- **Gate B/C 通过：** 6-8 旧 p000 有 2 个 Seed、55 段、1 条观测边；8-22 旧 p000/p001/p002 分别为 3/1/4 个 Seed、43/15/36 段、2/0/5 条观测边。均有 OpeningSeed、逐段状态及五份独立复核文件，没有被旧全局 `COMPETING_PLANAR_PATCHES` 提前阻断。
- **Gate D 通过：** 8-22 旧 p004 有 1 个 `PARTIAL_FOV` Seed，分段 0、观测边 0、状态 UNRESOLVED；该场景虽选中另一个 PARTIAL，但 Confirmed=0 且场景不是 RESOLVED。六场景 PARTIAL 误计 confirmed 次数为 0。

## 当前首个失败层与后续审查

`FIRST_BAD_STAGE=PER_SEGMENT_DECK_DISAMBIGUATION_AND_OBSERVED_BOUNDARY`：外轮廓和逐段入口已经打通，但大量段出现多个合格平面（300/543），而可用于真实边界的 Profile/Face 观测极少，故无完整闭合。38/46 个 Seed 触及推断扫描边界；这一比例和大候选的多分段形态需检查 `perimeter_debug.ply/json`，不能直接断言 FOV 判别错误或真实舱形错误。尤其 6-8 p000 与 8-22 p000/p001/p002 的独立 PLY 需要与原始 PCD 叠加，确认 Seed 是否落在实际舱口、外向箭头是否指向甲板、竞争候选是否真为不同的宽甲板。未经人工审查，不继续调阈值或移植 C++。

Ubuntu 后续复现应从本分支提交检出，用相同清单 PCD 和配置，执行 R0/R1 单测、V1.4 冻结门和非 Quick CTest；若与本次 Windows 基线比较，优先核对输入 SHA、配置哈希、源码 SHA、逐段状态与点级归属，不把操作系统差异预设为根因。
