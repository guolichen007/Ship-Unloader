# V1.5-R1-S3 高度图候选框与分色点云复盘

## 本轮边界

本轮从 R1-S2 提交 `105516d4a7101dbb9773551f4ed26644c073caab` 创建独立分支 `feature/v1-5r1-heightmap-topology-recovery`。新增的是**研究侧候选区域定位器**，不改变冻结的 Production 主链，不修改旧 Local Deck、Profile Break、3D Face、Hypothesis 或 `v15.json`，也不把高度图轮廓当成 opening-side 钢边。若要把这条路线提升为生产主链，仍须进行架构评审。

用户提供的旧 PNG 只用于人工观察；算法输入是数据清单中经 SHA 校验的原始 PCD，通过严格 V1.5 解码器得到 XYZ。没有读取 Hatch 标注、已知舱数、旧 CNN 输出或旧 `hold_detector` 源码。单船 Development 场景的“最大稠密支持连通域”仍只是未核实的目标船启发式，不适用于多船自动选船。

## 从 R1-S2 到高度图定位

R1-S2 六场景把大尺度结构拆成 46 个 OpeningSeed、543 个周边段，300 段甲板歧义，0 个完整观测舱。本轮先解决**区域在何处**，不宣称解决厘米级钢边。2.5D 高度面是粗定位证据；原始 3D 点仍是将来边界精度的唯一来源。

实现顺序：严格 PCD → 0.5 m 原始格中位高度 → 稠密支持包络 → 多高度模态 → 每层低区连通组件 → 跨层父子关系 → 依据区域面积、填充率、局部高度差及四侧高度上升选择大盆地 → 0.15 m 细格只计算支持比例 → 原始坐标轴对齐候选框与分色点云。候选框大小来自组件范围，没有场景名、Proposal ID、已知舱数或固定 Hatch 长宽分支。四侧高度上升仅表示粗 2.5D 定位证据，不是 `OBSERVED_3D_FACE` 或最终钢结构证据。

为避免 4-16 舱内货物造成假拆分，同层且框重叠的子盆地可以合成一个候选框；为避免 8-22 三舱被高层合并，多个空间分离且更紧凑的子盆地保留独立。稀疏 raw occupancy 的内部孔洞不触发 Partial-FOV；`touches_true_crop_boundary` 只使用输入点云格范围的真实外边界。这仍不是完整的传感器视野模型。

研究参数保存在 `ship_perception/config/r1_heightmap_research.json`，原有 `v15.json` 未更改。结果保存两份配置哈希和输入、软件 SHA。PNG 由 NumPy 和 Python 标准库生成，无新增图像运行依赖。

## 可视化与点级归属

每场景提供：

- `height_surface.png`：严格 PCD 重建的 0.5 m 高度面。
- `height_levels.png`：多高度层着色图；实际层值见 JSON。
- `hatch_regions.png`：候选区域颜色、原始 XY 候选框和编号。
- `hatch_regions.ply`：灰色为未归属 raw 点，各候选区域使用不同颜色；附加同色候选框线点。
- `hatch_boxes.ply`：仅候选框的上下框与立柱，底部为区域代表高度，顶部为周边代表高度。它是定位框，不是钢边。
- `regions/rNNN_points.ply`：单独查看一个区域的原始点。
- `region_point_ownership.npz`：每种颜色严格对应的 raw point ID。
- `hatch_regions.json`：候选位置、粗轮廓、面积、高度差、跨层稳定度、细格支持比、四侧高度上升、裁剪边界和证据语义。

六场景全部解析二进制 PLY 的前 N 个原始点，逐点与 NPZ 归属和 JSON 颜色核对完全一致；没有用候选框的整根 Z 柱重新猜颜色。PNG、PLY、NPZ、原始 PCD 和运行 JSON 全部留在 Work/Data，不进入 Git。

## 复核顺序和剩余阻塞

先看 8-22 的三个框是否分别贴近三个大舱，再检查 4-16 的长框是否避开左侧船头低表面；重点审查 08-01 两个交错低区是否真为两个舱、08-08 的右端是否过宽、6-8 和 7-16 的裁剪边界。CloudCompare 可单独加载 `hatch_regions.ply`，或把原始 PCD 与 `hatch_boxes.ply` 叠加；检查任一区域可单开 `regions/rNNN_points.ply`。

本轮 FIRST_BAD_STAGE 的研发假设前移至 `HEIGHTMAP_TOPOLOGY_DECOMPOSITION`；粗定位已有可检查的改进，但**真实标定验收仍未完成**。下一步必须先由用户人工确认候选框与真实舱口的位置关系，然后才能确定哪些框可以作为 3D 边界细化的入口；不能把这些 2.5D 框直接改名为最终 Hatch Polygon。
